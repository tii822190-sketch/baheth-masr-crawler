# Baheth Masr Crawler

نظام محلي أولًا لاكتشاف صفحات المواقع وفهرستها. توجد قاعدة التشغيل في `db/crawler.sqlite` داخل المستودع، وتستخدمها GitHub Actions بالتتابع لمنع الكتابة المتزامنة. تنتقل نتائج الفهرسة اليومية بعد ذلك إلى جدولي البحث `search_pages` و`search_pages_fts` في قاعدة Turso الخارجية.

## كيف يعمل النظام

يمرّ العمل بثلاث مراحل مستقلة:

1. **اكتشاف المواقع والروابط:** يختار العنكبوت موقعًا واحدًا في كل تشغيل. يبدأ من `robots.txt` وملفات Sitemap، ويتابع ملفات Sitemap المتداخلة، ثم يضيف الروابط المقبولة إلى طابور `site_pages`. إذا لم يجد Sitemap صفحات كافية، يستخدم Chromium لاستخراج الروابط من الصفحة الرئيسية وبعض الصفحات التي تحتوي على نص عربي.
2. **فهرسة الصفحات:** يقرأ الزاحف الصفحات الموجودة في الطابور على دفعات وبعمال متوازية. يستخدم HTTP أولًا في الوضع `hybrid`، ثم ينتقل إلى Chromium إذا كانت الاستجابة غير مناسبة للفهرسة. بعد استخراج البيانات المطلوبة يحفظ النتيجة في `index_results` ويحذف الصفحة من الطابور.
3. **المزامنة مع Turso:** ينقل Workflow اليومي نتائج `index_results` إلى `search_pages` باستخدام `upsert` على `url`، ثم يعيد بناء جدول البحث النصي الكامل `search_pages_fts`. لا تُحذف الصفوف المحلية إلا بعد نجاح النقل والتحقق من العملية.

> لا يتحقق العنكبوت من كل رابط بطلب منفصل أثناء الاكتشاف. فحص الصفحة واستخراج بياناتها مؤجلان إلى مرحلة الفهرسة.

## قاعدة البيانات المحلية

تحتوي قاعدة `db/crawler.sqlite` على ثلاثة جداول تطبيقية:

| الجدول | الغرض | أهم البيانات |
| --- | --- | --- |
| `sites` | سجل المواقع ونقطة استكمال اكتشافها | الرابط، حالة الاكتشاف، و`discovery_cursor` |
| `site_pages` | طابور الصفحات المكتشفة | الموقع، الرابط، حالة الزحف، وعدد المحاولات |
| `index_results` | النتائج الجاهزة للنشر في محرك البحث | الرابط، العنوان، الوصف، الأيقونة، الكلمات المفتاحية، والمقتطف |

الجداول الثلاثة تُنشأ أو تُحدّث بواسطة `crawler/src/db.mjs` عند تشغيل CLI. يتحقق التهيئة من سلامة SQLite، ويعيد بناء الجداول القديمة عند الحاجة حتى تقبل حالات المواقع الحالية. توجد فهارس على حالة طابور الصفحات، والموقع، ورابط نتيجة الفهرسة.

## اكتشاف المواقع

يشغّل `tools/discovery-spider.mjs` اكتشاف موقع واحد في كل مرة. الموقع المختار هو أول موقع بحالة `pending`، أو موقع محدد عبر `DISCOVERY_SITE_URL`. لا تُستأنف المواقع بحالة `incomplete` افتراضيًا؛ يمكن تفعيل ذلك عبر `DISCOVERY_RESUME_INCOMPLETE=true`.

يطبّق الاكتشاف التطبيع على الروابط، مثل إزالة اسم المضيف `www`، والهاش، ومنافذ HTTP/HTTPS الافتراضية، ومعاملات التتبع. ويستبعد الملفات غير المناسبة، والروابط الإدارية، وصفحات البحث والتغذية والتقسيم الرقمي، وبعض الصفحات العامة مثل صفحات التواصل والخصوصية والشروط. الحد الافتراضي هو 5,000 صفحة مقبولة للموقع و2,000 Sitemap.

بعد انتهاء التشغيل تصبح حالة الموقع واحدة من الحالات التالية:

- `completed`: اكتمل الاكتشاف ضمن الحدود المتاحة.
- `incomplete`: وصل الاكتشاف إلى الحد الأقصى مع وجود صفحات أو ملفات Sitemap لم تُعالج بعد، وحُفظت نقطة الاستكمال.
- `not_pages`: لم ينتج المسار الاحتياطي صفحات محتوى مناسبة.
- `failed`: حدث خطأ أثناء التشغيل.

تُعدّ صلاحية الصفحات للمحتوى المؤرشف مسؤولية الزاحف، ولذلك يعيد الاكتشاف `validation: deferred_to_crawler`.

## فهرسة الصفحات

الأمر الأساسي هو `node crawler/src/cli.mjs manual`. قبل كل دفعة يعيد الصفحات التي توقفت بحالة `processing` إلى `pending`. ثم يختار الصفحات `pending` أو `queued`، وإذا لم توجد ينتقل إلى الصفحات `needs_review` التي لم تتجاوز حد المحاولات.

في الوضع `hybrid` يحلل الزاحف استجابة HTTP قبل تقرير كفايتها. إذا بدا HTML هيكلًا لتطبيق JavaScript بلا نص مستخرج كافٍ، أو صُنّف المحتوى `dynamic_content` أو `thin_content`، أو كانت الاستجابة غير HTML/خطأ HTTP، يعيد جلبها عبر Chromium headless. يقارن النص المستخرج من النسختين ويحتفظ بنسخة المتصفح إذا أعادت محتوى أكثر؛ وإلا يبقي استجابة HTTP ويسجل محاولة المتصفح وسبب عدم استخدامها في log التشغيل.

إذا رمى طلب HTTP خطأً أو انتهى بمهلة في وضع `hybrid`، يحاول الزاحف Chromium مباشرةً بدل تجاوز fallback. يسجل log سلسلة أسباب أخطاء HTTP والمتصفح، بما فيها `cause` و`errno` و`hostname`، عند توافرها. يمرر محدد Chromium خانة التوازي مباشرةً إلى الصفحة المنتظرة دون إسقاط الحجز؛ وضُبط GitHub Actions على صفحة ومتصفح واحدين في الوقت نفسه مع مهلة متصفح 30 ثانية لتجنب ضغط الذاكرة والاتصالات في صفحات البوابة الثقيلة. وتُعطى صفحات نطاقات `.gov.eg` إشارة تصنيف مرشحة لفئة «حكومة وخدمات عامة»؛ ولا تتجاوز هذه الإشارة فحوص المحتوى والجودة.

لا تُحفظ الصفحة في `index_results` إلا إذا كانت استجابتها HTML، وكان تصنيف جودتها `good`، وتجاوز النص المستخرج الحد الأدنى، وتوفرت الحقول: `url` و`title` و`description` و`icon_url` و`keywords` و`snippet`. تُطبع البيانات وتُصنّف وفق `taxonomy/search-taxonomy.json`، وتُعامل النتائج الصحية والدينية وغيرها كمرشحات تصنيفية لا كموافقة تحريرية تلقائية.

تنتقل الصفحة غير المكتملة أولًا إلى `needs_review` ثم تُتاح لإعادة المحاولة المحددة. لا تُصنّف `corrupt` ولا تُحذف من الطابور إلا بعد بلوغ حد المحاولات الفعلي؛ الفشل الأول أثناء مرحلة المراجعة لا يتجاوز هذا الحد. يبث log كل صفحة عند اكتمالها مباشرةً، ويحفظ الـartifact أحداث الصفحات في `primary-crawler-result.jsonl` مع ملخص الدفعة في `primary-crawler-result.json`. تشمل التفاصيل الصفحات الناجحة والفاشلة، وسبب الفشل والحقول الناقصة وحالة HTTP ونوع المحتوى وطريقة الجلب والمدة وعدد المحاولات ونصًا مقتطفًا ومحاولة المتصفح ونتيجة مقارنة HTTP/Chromium. لا تُضاف أعمدة تشخيص إلى قاعدة SQLite؛ وعند استنفاد المحاولات تنتقل الصفحة إلى `corrupt` وتُحذف من الطابور، مع بقاء تفاصيلها في سجل/artifact التشغيل.

## المزامنة اليومية مع Turso

يعمل Workflow **Sync Index Results to Turso** يوميًا عند `01:00 UTC`، ويمكن تشغيله يدويًا من GitHub Actions. ينفذ الآتي:

1. يتحقق من وجود جدول `search_pages` في Turso.
2. يرسل الصفوف المحلية على دفعات إلى Worker الإدخال، الذي يدمج العنوان والوصف والكلمات المفتاحية والمقتطف والدومين داخل `search_text`.
3. يحفظ في D1 الأعمدة الأساسية فقط: `url`, `title`, `description`, `icon_url`, `search_text`، ويحدّث فهرس FTS5 لكل رابط.
4. يحذف من SQLite الصفوف المحلية التي أُكد نجاح إرسالها فقط، داخل معاملة واحدة، ويتحقق من عدد الصفوف المحذوفة.
5. يفحص سلامة قاعدة SQLite ويتوقف دون حذف أي نتائج محلية إذا فشل Worker أو لم يؤكد استلام الدفعة كاملة.

يستخدم Workflow `INGEST_MAX_ROWS=0` لنقل كل النتائج المتراكمة. ويعيد المحاولة حتى خمس مرات مع تأخير تصاعدي عند فشل طلبات Worker. إذا فشل النقل بعد استنفاد المحاولات، يتوقف التشغيل ولا يحذف النتائج المحلية.

يتطلب Workflow السرّين التاليين في إعدادات المستودع:

| Secret | الوصف |
| --- | --- |
| `INGEST_URL` | رابط Worker الإدخال، مثل `https://baheth-masr-crawler.tii822190.workers.dev` |
| `INGEST_TOKEN` | نفس قيمة `INGEST_TOKEN` المعرفة في Cloudflare Worker |

## الجدولة والتزامن

| Workflow | الجدولة الافتراضية | الوظيفة |
| --- | --- | --- |
| **Discovery Spider** | `00:00` و`08:00` و`16:00 UTC` | اكتشاف موقع واحد وإضافة روابطه إلى الطابور |
| **Page Indexer** | كل ساعة باستثناء أوقات الاكتشاف و`01:00 UTC` | فهرسة ما يصل إلى 1,000 صفحة في التشغيل المجدول |
| **Sync Index Results to D1 through Worker** | يوميًا عند `01:00 UTC` | إرسال النتائج إلى D1 عبر Worker وتنظيفها محليًا |

تستخدم Workflows الثلاثة مجموعة التزامن `baheth-local-crawler-db` مع `cancel-in-progress: false`. لذلك ينتظر التشغيل الجديد انتهاء التشغيل السابق بدل الكتابة بالتوازي على ملف SQLite. تحفظ Workflows تغييرات `db/crawler.sqlite` في Git، ويرفع Workflow الفهرسة نسخة مؤقتة من القاعدة وملخص التشغيل لمدة سبعة أيام.

## التشغيل المحلي

يتطلب المشروع Node.js 22 أو إصدارًا متوافقًا مع الاعتمادات الحالية.

```bash
npm ci
npm test
npm run db:init
npm run crawl:manual
```

لتشغيل دفعة يدوية بإعدادات مخصصة:

```bash
CRAWLER_BATCH_SIZE=500 \
CRAWLER_MAX_PAGES=500 \
CRAWLER_CONCURRENCY=10 \
CRAWLER_FETCH_MODE=hybrid \
npm run crawl:manual
```

أهم إعدادات الفهرسة هي `CRAWLER_BATCH_SIZE` و`CRAWLER_MAX_PAGES` و`CRAWLER_CONCURRENCY` و`CRAWLER_BROWSER_CONCURRENCY` و`CRAWLER_BROWSER_BUDGET_MS` و`CRAWLER_PAGE_TIMEOUT_MS` و`CRAWLER_RETRIES` و`CRAWLER_REVIEW_RETRIES` و`CRAWLER_FETCH_MODE` و`CRAWLER_MIN_EXTRACTED_TEXT_CHARS` و`CRAWLER_BROWSER_BIN`. الوضع `hybrid` هو الوضع الافتراضي، ويمكن تغييره إلى `http` أو `browser`.

أهم إعدادات الاكتشاف هي `DISCOVERY_SITE_URL` و`DISCOVERY_MAX_PAGES_PER_SITE` و`DISCOVERY_MAX_SITEMAPS` و`DISCOVERY_TIMEOUT_MS` و`DISCOVERY_RESUME_INCOMPLETE` و`DISCOVERY_BROWSER_BUDGET_MS` و`DISCOVERY_BROWSER_SCROLL_STEPS`.

لتشغيل المزامنة محليًا، عرّف متغيري البيئة ثم شغّل السكربت:

```bash
INGEST_URL='https://baheth-masr-crawler.tii822190.workers.dev' \
INGEST_TOKEN='...' \
node tools/sync-to-ingest-worker.mjs
```

يمكن التحكم في المزامنة عبر `INGEST_BATCH_SIZE` و`INGEST_MAX_ROWS` و`INGEST_RETRIES`. أسماء الجداول المستهدفة ثابتة داخل Worker: `search_pages` و`search_pages_fts`.

## هيكل المشروع

```text
crawler/src/                   كود التهيئة والاستخراج والتصنيف والزحف
crawler/test/                  اختبارات Node.js
db/crawler.sqlite              قاعدة التشغيل المحلية المحفوظة في Git
taxonomy/search-taxonomy.json  تصنيف الكلمات والموضوعات
tools/discovery-spider.mjs     اكتشاف الروابط من Sitemap وChromium
tools/sync-to-ingest-worker.mjs إرسال النتائج إلى D1 عبر Worker الإدخال
.github/workflows/             Workflows الاكتشاف والفهرسة والمزامنة
```

يبدأ CLI افتراضيًا بالأمر `manual`. الأمر `init` يهيئ القاعدة ويتحقق من سلامتها ثم ينهي التشغيل دون فهرسة.
